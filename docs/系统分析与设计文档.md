# 检测实验室简易排班管理系统 — 系统分析与设计文档

> 题目：使用 AI 工具辅助完成检测实验室简易排班管理系统
> 交付物 1：系统分析与设计

---

## 一、业务理解

### 1.1 背景与痛点

检测实验室的日常工作围绕"样本"展开：不同委托方送来的样本（水质、土壤、空气、食品、纺织品等）需要在当天分配给检测人员处理。人工排班的痛点：

- 排班员需要同时考虑"谁会做什么（技能）、今天谁来上班（在岗状态）、每人能干多久（可用工时）"三件事，靠经验口算容易出错；
- 样本有优先级差异，紧急委托不能排到下午才安排；
- 临时请假、任务激增时，整个排班表需要重来；
- 老板关心"今天赚了多少、人够不够用"，但缺少即时数据支撑。

本系统的目标：把"当日任务量 + 人员技能/状态/工时"输入系统，一键生成一份**可行、可解释、可调整**的当日排班计划，并给出收益分析和预警。

### 1.2 用户角色

| 角色 | 关注点 | 对应功能 |
| --- | --- | --- |
| 实验室主管/排班员 | 今天任务排不排得下、谁干什么 | 智能排班、告警与建议 |
| 财务/管理者 | 收入、成本、利润 | 工作看板、统计报表 |
| 实验员 | 我今天要做什么、做多久 | 排班明细、人员使用状态 |

### 1.3 业务目标

1. 快速掌握当日任务量与可用人员（题目需求 1）；
2. 按规则自动生成排班计划（需求 2、3）；
3. 展示完成情况、人力使用、累计任务与收益分析（需求 4）；
4. 超载时给出预警与调整建议（需求 5）。

## 二、核心功能

对应题目交付物 2 的功能列表，本系统实现如下：

| 功能 | 说明 | 对应题目要求 |
| --- | --- | --- |
| 基础数据展示 | 看板展示当日任务量、在岗人员、可用工时、任务分布 | 需求 1 |
| 智能排班 | 一键生成当日排班，考虑技能、在岗状态、工时、优先级、效率与性价比 | 需求 2、规则 7、10 |
| 手动调整 | 人员配置页可切换在岗状态/修改技能/工时后重新排班 | 需求 3、规则 6 |
| 工作看板 | 任务完成率、人员概览、告警汇总 | 需求 4 |
| 人力统计 | 每人已分配工时、利用率、分配样本数 | 需求 4、规则 8 |

## 三、主要流程

### 3.1 排班主流程

```
录入当日任务量（按样本类型）
        ↓
工作量预测（需求工时 vs 可用工时）
        ↓
一键智能排班
        ↓
排班结果（明细 + 完成率 + 利润 + 告警）
        ↓
保存到历史（用于累计任务与趋势统计）
```

### 3.2 人员调整流程（需求 3 / 规则 6）

```
人员配置页修改（请假离岗 / 技能变更 / 工时调整）
        ↓
保存配置
        ↓
回到智能排班页，重新生成
        ↓
系统基于最新人员状态重排，并给出新的告警与建议
```

### 3.3 数据维护流程

```
样本配置页：维护样本类型参数（时长/价值/成本/优先级）
人员配置页：维护人员参数（技能/在岗/工时/时薪/效率）
顶栏"恢复默认数据"：一键还原出厂数据（历史统计保留）
```

## 四、数据结构

系统采用**本地 JSON 文件持久化**（server/data/db.json），共五类实体：

### 4.1 样本类型（samples）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 样本编号，如 "A" |
| name | string | 名称，如 "水质检测" |
| processMinutes | number | 标准处理时长（分钟/件） |
| unitValue | number | 单位业务价值（¥/件） |
| unitCost | number | 单位直接成本（¥/件） |
| priority | number | 优先级，1 最高 |

默认 5 类（题目要求至少 A~E）：水质、土壤重金属、空气颗粒物、食品微生物、纺织品甲醛。

### 4.2 人员（staff）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | number | 人员编号 |
| name | string | 姓名 |
| type | string | 类别：全职 / 实习生（题目要求至少两类） |
| skills | string[] | 技能范围，对应样本类型编号 |
| available | boolean | 在岗状态（规则 6 的手动调整对象） |
| workHours | number | 当日可用工时（小时） |
| hourlyRate | number | 时薪（¥/小时） |
| efficiency | number | 效率系数，实际工时 = 标准工时 ÷ 效率系数 |

默认 6 人：4 名全职（8h）+ 2 名实习生（4h），技能矩阵采用"相邻覆盖 + 交叉备份"设计，确保正常负载可排满、极端负载可触发告警。

### 4.3 当日任务（tasks）

`[{ sampleId: "A", count: 16 }, ...]`，按样本类型汇总的任务量（题目要求"任务量可按样本类型汇总"）。

### 4.4 排班结果（currentSchedule / history）

| 字段 | 说明 |
| --- | --- |
| assignments | 逐条分配记录：人员、样本、件次、实际工时 |
| unfinished | 未完成（积压）样本清单 |
| utilization | 每人已用工时、可用工时、利用率、分配明细 |
| summary | 完成数/率、收入、直接成本、人力成本、利润 |
| forecast | 需求工时、可用工时、缺口、预计完成率 |
| warnings | 告警与调整建议列表 |

历史排班按日期保存（同日覆盖），供"累计任务"统计与趋势图使用。

## 五、排班规则与算法

### 5.1 硬约束（必须满足）

1. **技能匹配**：人员技能范围必须包含样本类型；
2. **在岗状态**：离岗人员不参与分配；
3. **工时上限**：单人累计排班工时不得超过其可用工时（题目第 5 条）。

### 5.2 软目标（按题目规则 10 的顺序）

1. 高优先级、高单位毛利的样本先排（样本排序：优先级升序 → 单位毛利降序）；
2. 尽量完成更多样本，减少积压（贪心"能排尽排"）；
3. 同岗候选多时，优先选"效率高、成本低、负载轻"的人员；
4. 无法完成时，明确说明缺口并给出调整建议。

### 5.3 人员选择评分函数

```
score = 0.45 × 效率系数
      + 0.25 × (1 − 时薪/最高时薪)
      + 0.30 × (1 − 已用工时/可用工时)
```

三个分项依次对应"效益优先、成本优先、负载均衡"，权重 0.45/0.25/0.30。所有分项归一化到 0~1，逻辑简单可解释（不引入复杂数学优化模型，符合题目第 5 条 UI/模型要求）。

### 5.4 算法流程与复杂度

对排序后的样本队列逐个执行：筛选候选（技能 + 剩余工时足够）→ 评分排序取最优 → 扣减剩余工时。单次排班时间复杂度 O(N·M·logM)（N 为样本总数、M 为人员数），N≤数千时毫秒级完成，满足"简易系统"定位。

### 5.5 告警规则（需求 5 / 规则 9）

| 触发条件 | 级别 | 建议 |
| --- | --- | --- |
| 存在未完成样本 | 严重 | 增派技能匹配人员 / 延长工时 / 协商交期 |
| 单人利用率 ≥ 95% | 提示 | 关注负载，必要时支援 |
| 全部排满且总工时耗尽 | 提示 | 新增任务前先评估人手 |

## 六、成本效益计算公式（题目规则 11）

```
利润 = 样本收入 − 样本直接成本 − 人力成本

样本收入    = Σ(完成样本数 × 单位业务价值)
样本直接成本 = Σ(完成样本数 × 单位直接成本)
人力成本    = Σ(实际排班工时 × 时薪)
```

其中实际排班工时 = 标准处理时长 ÷ 人员效率系数（实习生效率 < 1，实际耗时更长、人力成本按实际工时计，公式口径与题目一致）。

## 七、系统架构

```
┌────────────────────┐      ┌─────────────────────────┐
│ 前端 React (Vite)  │ HTTP │ 后端 Node.js + Express   │
│  看板/排班/配置/报表 │ ────→ │  排班算法 scheduler.js    │
│  ECharts 图表       │ /api │  数据持久化 store.js      │
└────────────────────┘      │  JSON 文件 (data/db.json) │
                            └─────────────────────────┘
```

- 开发模式：前端 5173（Vite 代理 /api → 3001）+ 后端 3001；
- 生产模式：前端 `npm run build` 后由后端单进程托管，访问 http://localhost:3001 即可（演示最简路径）。

### API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/state | 全量状态（样本/人员/任务/排班/历史摘要） |
| PUT | /api/samples | 保存样本配置 |
| PUT | /api/staff | 保存人员配置（含在岗状态调整） |
| PUT | /api/tasks | 保存当日任务量 |
| POST | /api/predict | 工作量预测 |
| POST | /api/schedule | 生成排班 |
| POST | /api/schedule/save | 保存排班到历史 |
| POST | /api/reset | 恢复默认数据（加分项 1） |

## 八、技术栈与选型理由

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18 + Vite 6 | 题目允许任意框架；组件化便于维护（评分项 10%） |

## 九、真实实验室部署方案与能力缺口（加分项 4）

### 9.1 部署方案

本系统为"1 天排班模拟"的课程原型。若落地到真实实验室，建议分三步：

第一步（小规模试用）：部署在一台实验室内部主机（Windows Server 或 Ubuntu），执行 `npm install && npm run build && npm start`，排班员与主管通过内网浏览器访问。数据存本地 JSON，每天下班前由管理员手动备份 data/db.json。

第二步（多用户正式化）：将 JSON 存储替换为 MySQL/PostgreSQL，增加登录与角色权限（排班员、实验员、主管），人员数据对接考勤系统自动同步在岗状态，样本数据对接 LIMS（实验室信息管理系统）自动导入任务量，避免手工录入。

第三步（智能化增强）：排班算法升级为带约束求解的优化引擎（如 OR-Tools），支持多天滚动排班、跨技能培训推荐、季节性负载预测；报表增加周/月维度成本核算，对接财务系统。

### 9.2 能力缺口清单

| 缺口 | 当前状态 | 落地前需补充 |
| --- | --- | --- |
| 用户与权限 | 无登录 | 角色权限、审计日志 |
| 数据来源 | 手工录入/默认数据 | 与 LIMS、考勤系统对接 |
| 存储可靠性 | 单 JSON 文件 | 数据库 + 定时备份 |
| 排班窗口 | 仅 1 天 | 多天滚动、跨天任务 |
| 突发任务 | 需手工重排 | 任务到达即触发的增量重排 |
| 真实排班软约束 | 未覆盖 | 连续工时上限、午休、跨实验室协作等 |
